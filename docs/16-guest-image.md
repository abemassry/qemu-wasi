# The guest disk image

**What this covers.** The project boots an Alpine Linux desktop from the
disk image `m.qcow2` in the m-browser directory.  This chapter describes
what is in that image, why it is configured the way it is, how to look
inside it and change it without breaking it, and how one could build a new
one.  Read it before changing the guest, or when something inside the
guest (X, Chromium, the network) misbehaves.

The image is not in git (it is about 2 GB).  Keep a copy on the team's
shared storage, and a backup before any change.

## The image at a glance

| Item | Value |
|---|---|
| Distribution | Alpine Linux 3.23, x86_64 |
| Kernel | 6.18.16-0-virt (Alpine's "virt" kernel, made for virtual machines) |
| File | `m.qcow2` in the m-browser directory: qcow2 version 3, 2 GiB virtual size |
| Partitions | 1: `/boot` (300 MiB), 2: swap (512 MiB), 3: `/` (about 1.2 GiB, ext4) |
| Bootloader | extlinux (syslinux) |
| Init system | OpenRC (BusyBox init plus OpenRC services) |
| Desktop | user `m`; X (Xorg, modesetting driver, no acceleration), Fluxbox, Chromium |
| Network | DHCP on `eth0` (emulated Intel e1000): 10.0.2.15, gateway 10.0.2.2, DNS 10.0.2.3 |
| Memory needed | about 1 GiB (m-browser passes `-m 1024`) |
| Screen | X: 1280x800; text consoles: 720x400 |

A few words used below:

- A **partition** is a slice of a disk with its own filesystem; the
  partition table at the start of the disk says where each one is.
- The **bootloader** is the small program the firmware (SeaBIOS) starts;
  it loads the Linux kernel and the **initramfs**, a small temporary
  filesystem whose job is to find and mount the real root filesystem.
- **init** is the first program the kernel starts; here OpenRC, which
  starts the system's services.
- The **X server** (Xorg) owns the screen, keyboard and mouse; the
  **window manager** (Fluxbox) draws window frames and the taskbar.
- **Swap** is disk space the kernel uses as overflow memory: much slower
  than RAM, and much slower still under emulation.
- **qcow2** is QEMU's disk image format: the file grows as data is
  written, and an **overlay** is a qcow2 file that records only the
  changes made on top of another image, its **backing file**.

## How the guest boots

```text
 QEMU starts                       (m-browser: wasi_qemu_init)
   |
 SeaBIOS (firmware, m-browser/pc-bios/bios-256k.bin)
   |  finds the disk, runs the bootloader
 extlinux  (partition 1: extlinux.conf, menu hidden, 1 s timeout)
   |  loads vmlinuz-virt + initramfs-virt
 Linux kernel + initramfs
   |  loads disk drivers, mounts partition 3 as /  ("Mounting root: ok")
 OpenRC (init)
   |  services: devices, filesystems, swap, networking (DHCP), ...,
   |  local (/etc/local.d/*.start), then the console login for user m
 startx  ->  Xorg (modesetting, AccelMethod none)
   |
 ~/.fluxbox/startup: xmodmap; chromium about:blank &; exec fluxbox
   |
 Fluxbox desktop   (about 2-2.5 minutes after QEMU starts)
 Chromium window   (about 4 minutes after QEMU starts)
```

The timings are for the multi-threaded QEMU on a fast laptop on mains
power; see [15-performance.md](15-performance.md) for measurements and how
to repeat them.

**Note:** how X is started at boot was not recorded when the image was
made.  The running server is `/usr/libexec/Xorg -nolisten tcp :0 vt1
-keeptty -auth /home/m/.serverauth.<pid>`, which is what `startx` runs, so
the session is most likely an automatic login on the first console plus
`startx` from the shell's profile.  Check `/etc/inittab` and
`/home/m/.profile` in the image (unverified).

## Disk layout

The partition table is an MBR ("DOS") table, as Alpine's installer
writes for BIOS machines.  Sectors are 512 bytes.

| # | Type | First sector | Sectors | Size | Contents |
|---|---|---|---|---|---|
| 1 | Linux (83) | 2048 | 614400 | 300 MiB | `/boot`: `extlinux.conf`, `vmlinuz-virt`, `initramfs-virt`, the kernel's `config-6.18.16-0-virt` |
| 2 | Linux swap (82) | 616448 | 1048576 | 512 MiB | swap |
| 3 | Linux (83) | 1665024 | 2529280 | about 1.2 GiB | `/`, ext4, UUID `95db9445-3822-473e-bbbe-0f3eb28edf0c` |

`extlinux.conf` boots the label `virt`:

```text
DEFAULT menu.c32
PROMPT 0
MENU HIDDEN
TIMEOUT 10
LABEL virt
  LINUX vmlinuz-virt
  INITRD initramfs-virt
  APPEND root=UUID=95db9445-3822-473e-bbbe-0f3eb28edf0c modules=sd-mod,usb-storage,ext4 quiet rootfstype=ext4
```

`TIMEOUT` is in tenths of a second.  On Alpine, `extlinux.conf` is
normally generated by `update-extlinux` from `/etc/update-extlinux.conf`
(general Alpine knowledge): edit that file, not `extlinux.conf`, inside
the guest.

## The configuration, and why

### X without acceleration

`/etc/X11/xorg.conf.d/20-modesetting.conf`:

```text
Section "Device"
	Identifier "modesetting"
	Driver "modesetting"
	Option "AccelMethod" "none"
EndSection
```

By default the modesetting driver uses glamor, which does 2D drawing
through OpenGL.  The emulated PC has no GPU, so OpenGL runs on the CPU
(Mesa's llvmpipe) inside the emulated CPU: Xorg took about 30 minutes to
start.  Without acceleration it starts in seconds.

### Chromium

Alpine's `chromium` launcher reads every `/etc/chromium/*.conf` file and
adds `$CHROMIUM_FLAGS` to Chromium's command line.  `chromium.conf` (from
the package) sets `--ozone-platform-hint=auto`; the team added
`/etc/chromium/zz-fast.conf`, whose content is in
`tools/perf/guest/chromium-fast.cmds`:

| Flags | Why |
|---|---|
| `--disable-gpu --disable-gpu-compositing` | There is no GPU: no GPU process, no compositing through emulated OpenGL |
| `--disable-background-networking --disable-component-update --disable-sync --disable-default-apps --no-first-run --no-default-browser-check` | No background downloads, updates or first-run work competing with the user |
| `--hide-crash-restore-bubble` | Closing m-browser cuts the guest's power, so Chromium always believes it crashed; its "Restore pages?" bubble swallowed clicks on the menu button |
| `--renderer-process-limit=1` | Fewer processes, less memory |
| `--disable-features=Translate,MediaRouter,OptimizationHints,OptimizationGuideModelDownloading,AutofillServerCommunication,InterestFeedContentSuggestions,CertificateTransparencyComponentUpdater` | More background services off |

`/home/m/.fluxbox/startup` starts Chromium with `about:blank` instead of
its New Tab page (the line was `chromium &`).  The New Tab page kept the
guest busy for as long as it was shown (it loads remote content), so
clicks took about 50 s to be answered; with `about:blank` the guest
settles soon after the window appears and clicks are answered in 6-15 s.

**Note:** Chromium remembers its window size and position (in the current
image about 1170x755 at the top left of the screen).  Scripts that click
into it must not assume a position: `tools/perf/click-latency.sh` finds
the menu button on the screen.

### Memory

The guest needs about 1 GiB:

- with QEMU's default of 128 MiB, the desktop swapped constantly, X
  stalled, and the guest kernel dropped keystrokes;
- with 512 MiB, starting Chromium pushed about 100 MiB to swap, and the
  kernel spent about a sixth of its time reclaiming and compacting memory
  (the `kswapd` and `kcompactd` threads);
- with 1 GiB nothing is swapped.

m-browser passes `-m 1024` (in `src/app.rs`).  QEMU's memory, guest RAM
included, must fit in WebAssembly's 4 GiB address space, which also holds
the 256 MiB translation buffer and QEMU itself.

### The kernel

Settings from the image's kernel configuration (`/boot/config-6.18.16-0-virt`)
that matter here:

| Setting | Meaning | Consequence |
|---|---|---|
| `CONFIG_HZ=1000` | 1000 timer interrupts ("ticks") per second | Each tick costs thousands of emulated instructions.  QEMU coalesces them: time slices in the single-threaded build, the APIC tick slack in the multi-threaded build (see [15-performance.md](15-performance.md)) |
| `CONFIG_SMP=y`, `NR_CPUS=256` | Multiple CPUs | The multi-threaded build's 2-8 vCPUs are used |
| `CONFIG_PREEMPT_DYNAMIC=y` | Preemption mode chosen at boot | Default kept |
| Transparent huge pages "always" | Large memory pages | Booting with `transparent_hugepage=never` made no measurable difference |
| CPU vulnerability mitigations | Page-table isolation, retpolines | Booting with `mitigations=off` made no measurable difference |
| ZSWAP (off by default), ZRAM (module) | Compressed swap in RAM | Not used |

Kernel options can be tried without changing the image:
`KBOOT=1 KAPPEND="option=value" tools/perf/boot-timing.sh NAME` starts the
image's kernel directly with extra options.

### Screens and blanking

The X screen is 1280x800 pixels.  QEMU's display backend magnifies small
screens by 2 (`WASI_GFX_SCALE`) but not beyond 1600x1200, so X is shown at
its real size and the 720x400 text consoles (boot messages, the QEMU
monitor) at twice their size.

X blanks the screen after 10 minutes without input: the window then shows
black.  Move the mouse.

## Working with the image

**Pitfall:** never run two QEMUs on the same image file: two writers
corrupt a qcow2 image.  m-browser's GUI locks `m.qcow2` while QEMU runs,
but its headless mode does not lock anything.  Work on copies.

### Look inside without booting

`tools/perf/prepare-base.sh` makes a raw copy of the image in `WORK`
(default `tools/perf/work`) and extracts the kernel, initramfs and kernel
command line.  From the raw copy, `debugfs` reads files directly; the
`?offset=` suffix says where the partition starts, in bytes:

```sh
# in the qemu-wasi directory, after tools/perf/prepare-base.sh
cd tools/perf/work
/usr/sbin/debugfs -c -R "ls -l /etc/chromium" "base.raw?offset=$((1665024 * 512))"
/usr/sbin/debugfs -c -R "cat /home/m/.fluxbox/startup" "base.raw?offset=$((1665024 * 512))"
/usr/sbin/debugfs -c -R "cat /extlinux.conf" "base.raw?offset=$((2048 * 512))"
```

`-c` opens the filesystem read-only and without checking it.

**Pitfall:** do not run `e2fsck` (or `fsck`) on the image from the host:
the host's e2fsprogs may be older than the image's ext4 features.

### Get a root shell

The root password was unknown when this was written.  The image's own
kernel can be started with `init=/bin/sh`, which gives a root shell
without logging in:

```sh
# in the qemu-wasi directory
tools/perf/guest-shell.sh shell
# from another terminal:
echo 'cat /etc/os-release > /dev/ttyS0' > tools/perf/work/type-shell.fifo
cat tools/perf/work/serial-shell.log
```

It runs on a throwaway overlay: nothing reaches `base.raw` or `m.qcow2`.
Only the root filesystem is mounted, and no services run.

### Change the image

The safe procedure:

1. Write the changes as shell commands in a file, one per line
   (here-documents work; see `tools/perf/guest/chromium-fast.cmds`).
2. Apply them to a new overlay and test it:

   ```sh
   # in the qemu-wasi directory
   tools/perf/mkbase.sh change1 changed.qcow2 my-change.cmds perf-base.qcow2
   BASE=changed.qcow2 CLICKS=1 tools/perf/boot-timing.sh test1
   ```

3. When it works, apply the same commands to the real image.  Either make
   a standalone image from the overlay chain (next section), or boot
   m-browser with a backup of `m.qcow2` and make the same changes from the
   running desktop.

Small changes can also be made directly from a terminal in the running
desktop, as user `m` (with root rights only if the image allows it).

### Turn an overlay into a standalone image

Overlays made by the tools/perf scripts record their backing file as
`/out/NAME`, the path inside QEMU, so `qemu-img` on the host cannot
follow them.  Rewrite the paths to host paths first, on copies:

```sh
# in a scratch directory with copies of base.raw, perf-base.qcow2 and changed.qcow2
qemu-img rebase -u -b "$PWD/base.raw" -F raw perf-base.qcow2
qemu-img rebase -u -b "$PWD/perf-base.qcow2" -F qcow2 changed.qcow2
qemu-img convert -O qcow2 changed.qcow2 new-m.qcow2
qemu-img check new-m.qcow2
```

`rebase -u` ("unsafe") only rewrites the overlay's header; `convert`
copies the whole chain into one file.  Test `new-m.qcow2` in m-browser
(copy it to `m.qcow2` after making a backup).

**Note:** `perf-base.qcow2` contains the tools/perf guest logger, which
writes to the serial port every 10 seconds.  For an image meant for daily
use, make the overlay on `base.raw` instead.

### Back up and repair

- Back up: copy `m.qcow2` while m-browser is closed.
- Check: `qemu-img check m.qcow2` (m-browser closed).
- Repair: `qemu-img check -r all m.qcow2` (m-browser closed).  Damage
  usually comes from two QEMUs writing the image, which m-browser's lock
  now prevents in the GUI.

Closing m-browser is a power cut for the guest: the filesystems are not
unmounted.  ext4's journal makes that safe, and QEMU flushes the image
when it quits, but programs inside the guest see a crash (hence Chromium's
"Restore pages?" bubble).

## Building a new image (outline, untested)

The team has not done this; it is the standard way to install Alpine,
plus this chapter's settings:

1. Install Alpine x86_64 in a native QEMU with KVM (fast): a 2 GiB disk,
   `setup-alpine` with the "sys" disk mode, which creates the boot, swap
   and root partitions and extlinux.
2. Add the desktop: `setup-xorg-base`, then `apk add fluxbox chromium
   xterm` (and fonts), create the user, make the first console log in
   automatically and run `startx`, with a `~/.fluxbox/startup` like the
   one above.
3. Add `20-modesetting.conf` with `AccelMethod none`, and the Chromium
   settings (`zz-fast.conf`, `about:blank`).
4. Shut down cleanly, convert to qcow2 if needed
   (`qemu-img convert -O qcow2 disk.img m.qcow2`), and test in m-browser
   and with `tools/perf/boot-timing.sh`.

**Note:** `tools/perf/prepare-base.sh` expects an MBR partition table and
extlinux, as described above; the kernel's command line must keep the
initramfs's "Mounting root: ok" message (Alpine's initramfs prints it)
for the scripts to know the root filesystem is mounted.

## Pitfalls

- Two QEMUs on one image corrupt it; m-browser's headless mode does not
  lock the image.
- The guest is slow to shut down from inside (it is emulated): prefer
  closing m-browser, which powers the guest off after QEMU flushes the
  disk.
- If the guest's screen is black after a while, X has blanked it: move
  the mouse.
- Chromium keeps its profile (history, window geometry, open tabs) in
  `/home/m/.config/chromium`; tests on copies start from whatever state
  the image had when it was copied.
